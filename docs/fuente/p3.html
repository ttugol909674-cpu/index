6. Base de datos

La base de datos se implementó en MySQL 8.4 con motor InnoDB, juego de caracteres utf8mb4_unicode_ci y claves foráneas con acción ON DELETE CASCADE, de modo que al eliminar un usuario o una sede se borren en cascada sus datos dependientes y no queden filas huérfanas. El esquema definitivo está en db/schema.sql, los datos de prueba en db/seed.sql y la actualización del esquema en db/migracion.sql.

Cardinalidades. Un usuario tiene 0..N vehículos, 0..N reservas y 0..N presupuestos; cada reserva pertenece a exactamente un usuario, un vehículo, una sede y un servicio. Una reserva tiene 0..N cobros (puede ser 0 si todavía no pagó, o 2 si pagó un anticipo y luego el saldo) y 0..1 factura. Un presupuesto tiene 1..N ítems. Una sede tiene 0..N horarios (uno por día de la semana), 0..N marcas y 0..N servicios.

6.3 Normalización

1FN — valores atómicos. No hay grupos repetidos: los ítems de un presupuesto están en presupuesto_detalle (no en una columna items) y los horarios de una sede en taller_horario (no en columnas lunes, martes, …). Cada campo guarda un solo valor: reserva.fecha_reserva y reserva.hora_reserva están separados, igual que vehiculo.marca y vehiculo.modelo.

2FN — dependencia de toda la clave. Las tablas con clave compuesta son taller_horario (id_taller, dia_semana), permiso_rol (rol, permiso), taller_marca y taller_servicio. En todas ellas cada atributo depende de la clave completa: en taller_horario, hora_inicio y hora_fin dependen del día y de la sede, y no existe ningún atributo que dependa solo de id_taller (eso vive en taller). Las tablas de clave simple ya están en 2FN por definición.

3FN — sin dependencias transitivas. reserva.precio_total es un dato congelado a propósito: si dependiera de servicio.precio (que puede cambiar), el historial de lo cobrado se rompería al modificar la lista de precios. Congelarlo rompe la dependencia transitiva reserva → servicio → precio y da trazabilidad histórica. Del mismo modo, pago no guarda ni el nombre del cliente ni el de la sede: se llega por pago → reserva → usuario/taller, sin duplicar datos.

BCNF y 4FN. Todas las dependencias funcionales son de clave completa, por lo que el esquema cumple BCNF; y no existen dependencias multivaluadas fuera de las tablas de detalle, por lo que cumple 4FN.

6.4 Consultas, vistas y reportes

Los reportes que pide el enunciado («historial de servicios de un vehículo o la facturación por taller») se resuelven con JOIN entre varias tablas y, en los casos que lo requieren, con subconsultas que DEVUELVEN valores agregados. Un ejemplo real del historial del cliente:

SELECT r.id_reserva, r.fecha_reserva, r.hora_reserva, r.estado,
       r.precio_total, t.nombre AS taller, s.nombre AS servicio,
       v.marca, v.modelo, v.patente
  FROM reserva r
  JOIN taller   t ON t.id_taller   = r.id_taller
  JOIN servicio s ON s.id_servicio = r.id_servicio
  JOIN vehiculo v ON v.id_vehiculo = r.id_vehiculo
 WHERE r.cedula_usuario = ?
 ORDER BY r.fecha_reserva DESC, r.hora_reserva DESC;

Y la facturación por sede, que acumula los cobros válidos de cada taller:

SELECT t.nombre AS taller,
       COUNT(DISTINCT r.id_reserva)              AS turnos,
       SUM(r.precio_total)                       AS facturado,
       SUM(COALESCE(p.total_cobrado, 0))         AS cobrado,
       SUM(r.precio_total - COALESCE(p.total_cobrado, 0)) AS saldo
  FROM taller t
  JOIN reserva r ON r.id_taller = t.id_taller
  LEFT JOIN (SELECT id_reserva, SUM(monto) AS total_cobrado
               FROM pago WHERE estado = 'pagado' GROUP BY id_reserva) p
    ON p.id_reserva = r.id_reserva
 GROUP BY t.id_taller, t.nombre
 ORDER BY facturado DESC;

La aplicación también ofrece vistas lógicas mediante consultas reutilizables en funciones_pago.php (estado de cobro de una reserva, totales por sede) y subconsultas en las pantallas de agenda y de cobros para mostrar el total adeudado sin recalcularlo en PHP.

6.5 DDL, datos de prueba y migración

El esquema se entrega como DDL en db/schema.sql (16 tablas con sus claves, índices y restricciones), y los datos de prueba como un conjunto de INSERT en db/seed.sql (5 usuarios de los tres roles con sus vehículos, 2 sedes con horario, marcas y servicios, 3 servicios, reservas en distintos estados, pagos, presupuestos y una cuenta bancaria). El proceso de instalación carga ambos archivos de forma automática la primera vez que se crea el volumen de datos.

Además, db/migracion.sql es un script idempotente que aplica cambios de esquema sin perder datos (agrega columnas, crea tablas nuevas y agrega índices solo si no existen). Esto permitió evolucionar el modelo durante el proyecto sin perder la información ya cargada, que es justamente lo que exige el enunciado cuando pide registrar la documentación de los cambios.

Ejemplo de uso. El siguiente fragmento muestra cómo se añade una columna sin duplicarla en una segunda ejecución:

ALTER TABLE usuario
  ADD COLUMN IF NOT EXISTS saldo_prepago DECIMAL(10,2) NOT NULL DEFAULT 0.00;

7.2 Backend: PHP, PDO, sesiones y CSRF

Todo el acceso a datos pasa por una única conexión PDO definida en config.php y reutilizada por conexion.php. El acceso se hace siempre con consultas preparadas, nunca concatenando datos del usuario:

$stmt = $conexion->prepare('SELECT * FROM usuario WHERE email = ? AND rol = ?');
$stmt->execute([$email, $rol]);
$usuario = $stmt->fetch(PDO::FETCH_ASSOC);

La sesión se inicia con cookie httponly y SameSite=Lax, y el identificador se regenera al iniciar sesión para evitar la fijación de sesión. El token CSRF se genera una vez por sesión y se valida en cada POST:

function csrfToken(): string {
    if (empty($_SESSION['csrf_token'])) {
        $_SESSION['csrf_token'] = bin2hex(random_bytes(32));
    }
    return $_SESSION['csrf_token'];
}

function validarCsrf($tokenRecibido): bool {
    if (empty($_SESSION['csrf_token']) || !is_string($tokenRecibido) || $tokenRecibido === '') {
        return false;
    }
    return hash_equals($_SESSION['csrf_token'], $tokenRecibido);
}

La autorización se hace con permisos y no con roles, lo que permite reconfigurar el sistema desde la interfaz sin tocar el código:

function verificarPermiso(string $permiso): void {
    exigirSesion();
    if (!tienePermiso($permiso)) {
        header('Location: error_403.php');
        exit();
    }
}

7.3 Interfaz, bilingüismo y accesibilidad

La interfaz usa una paleta institucional azul sobre fondo oscuro, común a las 42 pantallas mediante css/tgs-panel.css. El bilingüismo se resuelve con archivos de textos por idioma y un selector ES/EN en la cabecera de cada pantalla; el idioma elegido se guarda en la sesión, de modo que se conserva al navegar y sobrevive al inicio de sesión. Una auditoría automática verifica que las 24 pantallas revisadas no mezclen idiomas y que todas tengan el selector.

En accesibilidad se suelen aplicar: contraste alto, foco visible, etiquetas asociadas a los campos, textos alternativos en los mapas y mensajes de estado expresados con texto (no solo con color).

7.4 Paneles por rol

El sistema presenta tres paneles distintos según el rol de la sesión. El panel del administrador se muestra a continuación.

7.5 Reservas y disponibilidad

El corazón del sistema es el módulo de disponibilidad (taller_disponibilidad.php). Cada sede tiene un horario semanal (taller_horario) y una capacidad de turnos simultáneos (taller.capacidad). Las franjas son de 60 minutos desde la hora de apertura y la disponibilidad se calcula contando las reservas vivas de esa franja: las canceladas no ocupan lugar.

7.6 Pagos, presupuestos y facturación

El módulo de pagos implementa el circuito completo: el cliente ve su saldo, los datos bancarios de la empresa con el código QR y el importe pendiente; puede pagar con su saldo prepago (queda pagado al instante) o reportar un pago con el comprobante; el gestor valida o rechaza ese cobro desde la cola de cobros reportados, y en ese momento se recalcula el estado de la reserva y se emite la factura.

7.7 Notificaciones por correo

El módulo de avisos registra siempre la notificación en la base (tabla notificacion) y la envía solo si hay transporte de correo configurado; si no lo hay, queda en estado pendiente y se puede reenviar después. El cliente SMTP propio implementa el diálogo completo (EHLO, autenticación, MAIL FROM, RCPT TO, DATA) con soporte de TLS y de STARTTLS.

7.8 Gestión administrativa
