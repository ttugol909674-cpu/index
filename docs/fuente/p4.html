8. Seguridad de la información

La seguridad no es un agregado del final: es una condición de diseño transversal, presente en cada una de las 42 pantallas. Este capítulo resume los controles implementados, la evidencia de cada uno y el resultado de su verificación.

8.1 Autenticación y gestión de sesión

  • Almacenamiento de claves: se usa password_hash() con bcrypt (PASSWORD_DEFAULT) y la verificación con password_verify(). Las claves nunca se guardan ni se comparan en texto plano.
  • Cookie de sesión: httponly (no accesible desde JavaScript), SameSite=Lax (corta el envío de cookies en peticiones de terceros) y secure automático si lasitio se sirve por HTTPS.
  • Regeneración del identificador: tras autenticarse se llama a session_regenerate_id(true), lo que evita la fijación de sesión.
  • Error genérico: el mensaje de login no distingue entre correo inexistente y clave incorrecta, para no permitir enumeración de usuarios.

8.2 Protección contra CSRF

Todos los formularios POST incluyen un token oculto y son validados en el servidor antes de ejecutar la acción. La suite test_csrf.sh verifica, entre otros casos, que un POST sin token válido no modifica nada, que el token de otra sesión se rechaza, y que el token se consume de forma coherente.

8.3 Prevención de inyección SQL

Todas las entradas del usuario llegan a la base como parámetro de una consulta preparada. Los identificadores que necesitan concatenarse se castean antes (intval(), FILTER_VALIDATE_INT). Durante la revisión del proyecto se detectó que cuatro páginas (portada, alta y edición de sede, gestión de sedes) ainda usaban la API antigua mysqli con SQL construido por concatenación; se migraron a PDO, con lo que el proyecto queda con una única vía de conexión y sin SQL construido a mano en ningún punto del código.

8.4 Control de acceso por permisos

La matriz de permisos declara 29 permisos para tres roles. El código define los valores por defecto y la tabla permiso_rol guarda las modificaciones que haga el administrador desde permisos.php: si no hay fila para un par (rol, permiso), manda la matriz del código; si la hay, manda la tabla. Los tres permisos críticos (ver_panel_admin, ver_matriz_permisos, editar_matriz_permisos) no se pueden deshabilitar, para que el sistema nunca quede sin administración.

Además, cada página comprueba la propiedad del recurso, no solo el permiso: un cliente no puede ver ni modificar la reserva de otro cliente porque la consulta filtra por la cédula de la sesión (prueba test_ownership.sh).

8.5 Manejo de errores y exposición de información

El contenedor usa php.ini-production con display_errors=Off y log_errors=On; el detalle real queda en el log del contenedor y el visitante ve un mensaje genérico. Se corrigió además el caso en que las páginas se ejecutaban con display_errors=On durante las primeras entregas, lo que exponía detalles internos en pantalla.

8.6 Protección de los datos de la empresa y de la base

Los datos bancarios que ve el cliente (alias, CBU y QR) se cargan desde el panel del administrador y se muestran solo si están activos; ningún cliente puede crearlos ni modificarlos. Las credenciales de la base de datos no están en el código: viven en .env (plantilla versionada) y .env.local (valores locales, ignorado por Git).

Además, el acceso a MySQL está segmentado por roles (capítulo 6.4.1): la aplicación usa el usuario tgs, los informes y la auditoría usan tgs_lectura, que solo puede consultar, y la administración de la base usa tgs_admin. Así, si un usuario de solo lectura se compromete, no puede modificar los datos del negocio.

El sitio se publica con Cloudflare Tunnel (capítulo 11.7), de modo que queda disponible desde internet sin abrir puertos en el router. Al estar expuesto, el proyecto suma dos controles específicos:

  • Registro controlado: el registro de cuentas se puede cerrar (REGISTRO_ABIERTO=0) o proteger con un código (REGISTRO_CODIGO), sin tocar el código. Así el requisito de registro del enunciado se cumple y, a la vez, nadie puede darse de alta por su cuenta mientras el sitio esté abierto al público.

11.3 Política de respaldo y recuperación

Tarea programada. El respaldo se automatizó con una entrada de crontab del usuario del servidor, que ejecuta scripts/respaldar.sh todos los días a las 3:17 y deja el log en backups/cron.log:

17 3 * * * /bin/bash /home/taller/Desktop/tgs/scripts/respaldar.sh \
             >> /home/taller/Desktop/tgs/backups/cron.log 2>&1

La rotaciónautomática (conservar los cinco respaldos más recientes) evita que el disco se llene, y la restauración se probó en la defensa con el guion del video de caída.

11.4 Seguridad de los servidores

La máquina virtual aplica las medidas básicas de un servidor de centro de cómputos: gestión de la base de datos con un usuario de aplicación (tgs) sin permisos administrativos (el root se usa solo para los respaldos), actualizaciones de seguridad automáticas mediante unattended-upgrades, y el firewall con iptables que documenta el script scripts/firewall.sh.

11.7 Publicación del sitio en internet

La máquina virtual del proyecto vive en una red doméstica, detrás del router y sin dirección IP pública. Para presentar el sistema fuera de esa red (por ejemplo, desde el aula de la UNT en la defensa) se usa Cloudflare Tunnel: el servidor se conecta hacia afuera a Cloudflare y Cloudflare reenvía el tráfico a la aplicación. No hay que abrir puertos ni tocar la configuración del router, y el sitio queda con HTTPS (certificado automático).

Script / acciónQué hace
bash scripts/tunel.sh iniciarLevanta el túnel y publica la URL pública en la salida estándar

La URL que entrega el modo temporal tiene la forma https://<palabras>.trycloudflare.com y cambia cada vez que se reinicia el túnel. Para un nombre permanente hay dos caminos libres:

  • Cloudflare con un dominio propio: se crea una cuenta gratuita en Cloudflare, se apunta el dominio a sus servidores y se declara un túnel con nombre; el sitio queda en https://tgs.<tu-dominio> con certificado automático.
  • Subdominio gratis con DuckDNS o FreeDNS: servicios que dan un subdominio gratuito (por ejemplo tgs.duckdns.org) que se actualiza desde el propio servidor con una tarea programada. El subdominio se configura como nombre público del túnel de Cloudflare.

Seguridad previa a publicar. Antes de exponer el sitio se corrigió una falla real: Apache servía todos los archivos de la carpeta del proyecto, de modo que /.env.local entregaba la clave de root de MySQL y /.git/ el historial completo del repositorio. El archivo .htaccess del proyecto bloquea ahora los archivos ocultos, el historial de Git y las carpetas sensibles (db/, docs/, scripts/, backups/), y agrega cabeceras de seguridad básicas. La verificación se hace con peticiones reales contra el sitio publicado, no solo de forma local.

El sitio publicado mantiene el mismo acceso del sistema interno: la sesión, los permisos por rol y la matriz de permisos siguen siendo los que se describen en el capítulo 8. Para una demostración pública conviene cambiar las claves de las cuentas de prueba y restringir el registro abierto.

13. Conclusiones y trabajo futuro

13.1 Conclusiones

El proyecto cumple el objetivo general: se desarrolló una plataforma web completa e integrada que permite registrarse, reservar servicios mecánicos, planificar los mantenimientos según la disponibilidad real de cada sede, gestionar presupuestos, cobrar y facturar, con herramientas de administración para la empresa.

Los 40 requisitos del enunciado quedan implementados y verificados, incluidos los cinco puntos que faltaban en la revisión intermedia (factura electrónica, historial por vehículo, vista detallada de sede, filtros por marca y servicio, y pago directo con cuenta prepaga), y cada uno tiene su prueba automatizada asociada.

La calidad técnica se apoya en cuatro decisiones que resultaron determinantes: una única conexión PDO con consultas preparadas en todo el proyecto; un modelo de autorización por permisos en lugar de por roles, editable sin tocar el código; la validación de la disponibilidad en el servidor, de modo que el cliente nunca puede forzar un turno inválido; y una suite automatizada que se ejecuta antes de cada entrega y detectó errores reales, varios de los cuales se corrigieron durante el proyecto.

El despliegue en Docker con scripts de operación, respaldo automático y restauración probada hace que la solución sea reproducible y demostrable: cualquiera puede instalarla con un comando y, si el servidor cae, recuperarla en minutos durante la propia defensa.
