1. Resumen

Este documento presenta el desarrollo completo del proyecto TGS — Taller Global de Servicios, una plataforma web que permite a los clientes de una red de talleres mecánicos registrar sus vehículos, agendar turnos de servicio, consultar el historial de mantenimiento, pagar los servicios y descargar sus facturas; al gestor de taller le permite gestionar la agenda del día, validar los pagos reportados y emitir presupuestos; y al administrador le permite administrar usuarios, sedes, servicios, la matriz de permisos y los datos bancarios de la empresa.

El sistema no es una maqueta: es una aplicación completa que funciona de punta a punta sobre una máquina virtual Ubuntu 26.04 con Docker Compose, dos contenedores (Apache + PHP 8.4 y MySQL 8.4), un volumen persistente para la base, scripts de instalación, respaldo, restauración y simulación de caída, y una suite automatizada de 28 pruebas end‑to‑end más 20 casos de verificación de requisitos, todos en verde. La base de datos tiene 16 tablas normalizadas hasta 3FN, con datos de prueba cargados por script y una migración idempotente que permite evolucionar el esquema sin perder información.

La seguridad se resolvió con consultas preparadas (PDO) en el 100 % de las operaciones, cifrado de contraseñas con bcrypt, token CSRF en todos los formularios POST, matriz de permisos por rol editable en caliente y gestión de errores que nunca muestra detalles al visitante. La interfaz es bilingüe (es/en) y responde a tres perfiles de uso distintos, con 24 pantallas documentadas en este documento mediante capturas reales del sistema en funcionamiento.

2. Introducción

2.1 Contexto y problemática

Las redes de talleres mecánicos suelen resolver la gestión de turnos por cuaderno, por WhatsApp o por llamadas telefónica. Eso genera tres problemas habituales: el cliente no sabe con certeza si su vehículo está siendo atendido ni cuándo estará listo; el taller no sabe con anticipación cuántos lugares tiene disponibles para el día siguiente y termina aceptando reservas que no puede cumplir; y, cuando el trabajo termina, la facturación y el cobro quedan en un papel que se pierde o se transcribe a mano con errores.

La empresa cliente del proyecto, TGS — Blue Tech Uruguay, planteó la necesidad de una plataforma única que ordene el ciclo completo del servicio: agendar, atender, presupuestar, cobrar y documentar. El enunciado oficial (ANEP–DGETP, Proyecto de Pasaje de Grado) precisa el alcance: una página web y una aplicación integrada que permita registrarse, agendar servicios, mostrar un mapa con los talleres y su ubicación, considerar la disponibilidad de lugar por sede, realizar reservas y efectuar pagos, con herramientas de gestión para la administración de TGS.

2.2 Justificación del proyecto

El proyecto se justifica en cuatro planos:

  • Funcional: cubre los 40 requisitos funcionales del enunciado, organizados en tres roles (cliente, gestor de puntos de carga y administrador) tal como fueron especificados.
  • Técnico: la aplicación se despliega de forma reproducible en cualquier equipo con Docker, con la configuración externalizada y un juego de scripts que permiten instalarla, respaldarla, restaurarla y simular una caída del servidor durante la defensa.
  • Académico: la solución aplica de forma explícita los contenidos de Programación Full Stack (base de datos, backend, conexión), Ingeniería de Software (UML, lógica del sistema, diseño de interfaz, control de versiones, plan de pruebas) y Administración de Sistemas Operativos (servidor, respaldos, seguridad, automatización).
  • Social: al digitalizar la reserva y el cobro se reduce la barrera de entrada para personas con menos familiaridad con la informática y se mejora la вклюión digital de los clientes mayores o con movilidad reducida, que pueden agendar y pagar desde el celular.

2.3 Objetivo general y objetivos específicos

El objetivo general del proyecto es desarrollar una solución tecnológica que cumpla los requisitos planteados por la empresa mediante la creación de una página web y una aplicación integrada, capaz de ofrecer a los usuarios registrarse, reservar servicios, planificar los mantenimientos considerando los talleres disponibles y realizar pagos de manera segura.

Los objetivos específicos tomados del enunciado se operationalizaron así:

  1. Diseñar una base de datos para almacenar la información del negocio (modelo normalizado 3FN, 16 tablas, DDL y datos de prueba en scripts versionados).
  2. Implementar un servidor web reproducible (Apache + PHP 8.4 en Docker sobre Ubuntu, con MySQL 8.4 como gestor de base de datos).
  3. Crear una interfaz de usuario atractiva, intuitiva y fácil de utilizar (diseño unificado en tres paneles, navegación coherente, validación en cliente y servidor, mensajes de error claros).
  4. Implementar un sistema de inicio de sesión que permita a los administradores gestionar la información (sesiones con cookies protegidas, regeneración de identificador, matriz de permisos por rol).
  5. Garantizar la seguridad de la información de los usuarios (CSRF, bcrypt, consultas preparadas, escape de salida, control de errores, cookies httponly y SameSite).
  6. Asegurar que la solución sea robusta y libre de errores aplicando pruebas exhaustivas (28 suites end‑to‑end, 20 casos de verificación, auditoría de sintaxis y de warnings).
  7. Optimizar el sitio web para una carga rápida y una experiencia de usuario mejorada (caché de recursos, consultas indexadas, imágenes optimizadas, paginación de listados).

3. Marco teórico y metodología

3.1 Metodología de desarrollo: Scrum

El desarrollo se organizó con un enfoque ágil Scrum, con iteraciones cortas (sprints) y entregables verificables al final de cada una. La decisión se tomó porque el enunciado define el producto en términos de "funcionalidades" verificables por rol, lo que se traduce naturalmente a historias de usuario y a criterios de aceptación observables.

3.2 Modelo de arquitectura en tres capas

La aplicación se organizó con una arquitectura de tres capas, que separa las responsabilidades y permite que el mismo código sirva a los tres roles sin duplicación:

CapaResponsabilidadArchivos
Presentación (front‑end)HTML, CSS y JavaScript de cada pantalla; formularios; validación de cliente; mensajes42 archivos .php de vista, css/tgs-panel.css, css/tema-tgs.css, lang/es.php, lang/en.php
Lógica de negocio (back‑end)Autenticación, autorización, sesión, CSRF, reglas de disponibilidad, cálculo de importes, envío de correo, facturaauth.php, correo.php, taller_disponibilidad.php, funciones_pago.php, conexion.php, config.php
DatosEsquema, consultas preparadas, migraciones, datos de pruebaMySQL 8.4, db/schema.sql, db/seed.sql, db/migracion.sql

El control de acceso se resuelve en la capa de negocio mediante una matriz de permisos (29 permisos × 3 roles) declarada en el código y almacenada en la tabla permiso_rol, que el administrador puede modificar desde la pantalla permisos.php. Cada página pide el permiso que necesita con verificarPermiso(); si el usuario no lo tiene, se lo envía a la página de acceso denegado. De esta forma, cambiar un permiso se resuelve en un solo lugar y no exige tocar el código de las pantallas.

3.4 Fundamentos de seguridad web

El proyecto aplica los controles de seguridad web habituales de OWASP, y cada uno tiene su implementación concreta:

ControlImplementación en el proyecto
AutenticaciónContraseñas con password_hash() (bcrypt, PASSWORD_DEFAULT) y verificación con password_verify(); el error del login es genérico para no revelar si el correo existe
CSRFToken por sesión generado con random_bytes(32), verificado con hash_equals() en todos los formularios POST
Inyección SQLConsultas preparadas con PDO en el 100 % de las operaciones; los identificadores se castean con intval() o FILTER_VALIDATE_INT
XSSSalida escapada con htmlspecialchars(); el único HTML sin escapar es el iframe del mapa, que se guarda y se muestra con control
Control de accesoMatriz de permisos por rol, comprobada en servidor en cada página y en cada acción sensible
Gestion de cookiesCookie de sesión con httponly y SameSite=Lax, secure si hay HTTPS, y session_regenerate_id(true) tras autenticarse
Filtrado de erroresdisplay_errors=Off y log_errors=On: el visitante ve un mensaje genérico y el detalle real queda en el log del contenedor
Gestión de secretosCredenciales fuera del código: variables de entorno (.env versionado con valores de ejemplo y .env.local local, nunca versionado)

3.5 Metodología de pruebas

Se combinaron las dos familias de prueba que pide el enunciado:

  • Caja negra (funcionales): se verifican las salidas del sistema a partir de las entradas del usuario, sin depender del código. La herramienta es curl sobre la aplicación real en Docker, con un script reutilizable que inicia sesión real y obtiene el token CSRF de cada página. Se escribieron 28 suites que cubren los 40 requisitos y 20 casos adicionales de verificación de las brechas G1–G5.
  • Caja blanca (estructurales): se revisa el código y la base: auditoría de sintaxis de los 42 archivos PHP, búsqueda de consultas concatenadas, verificación de que todo formulario POST lleva token CSRF, revisión de que no queden páginas con errores PHP y control de que la base no tenga filas huérfanas ni claves foráneas rotas.
